## ベースイメージと影響確認

最初に Debian 13 へ更新して実イメージをスキャンしましたが、ワーカーの FFmpeg などに
動画処理に関わる未修正検出が残りました。最終的に API とワーカーを公式 Alpine ベースへ
変更し、ダイジェストを固定しました。Python はロックした配布済み wheel だけを使用します。
API からは npm の両インストール先と実行コマンドを除去しています。

| ローカル ARM64 イメージ | Debian 12 時点の HIGH/CRITICAL 検出 | Debian 13 試行 | 最終 Alpine |
| --- | ---: | ---: | ---: |
| API | 57 | 43 | 0 |
| ワーカー | 275 | 208 | 0 |
| Web | 0 | 対象外 | 0 |

件数はパッケージ・アドバイザリの検出数で、重複を除いた CVE 件数ではありません。
Trivy 0.76.1 の当日の DB を使用し、未修正版や特定 CVE の除外は追加していません。
[最終イメージ識別子と検証結果](onprem-hardening-images-2026-10-23.json)に記録しました。
ローカル識別子は公開レジストリの配布用 digest ではありません。スキャン結果はこの時点の
実イメージに対する結果であり、未知の問題や将来の DB 更新後の無検出を保証しません。

Node/Python/uv と npm/pip の生成ブロックを既存の Runtime Updates へ統合しました。
オンプレのイメージだけ古いバージョンへ取り残されないことも更新テストで確認しています。

全体の開発・文書依存には引き続き [braces の未修正問題](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)が残ります。
API の本番依存をインストールした際の npm audit は 0 件でしたが、リポジトリ全体を
脆弱性ゼロとは扱いません。既存の通知と資格情報を分離したビルドを維持します。

## Kubernetes での更新・復元

専用 kind クラスタ上の PostgreSQL 17/pgvector、Garage、ElasticMQ を使用しました。
これらの基盤は検証専用で、アプリの Helm Chart に含めていません。
推論は固定応答の HTTP サーバーです。モデルの認識・回答品質を検証したものではありません。

1. マイグレーションフックを経て API・Web・ワーカーを導入。
2. 動画を署名付き URL でアップロードし、キューと実際の FFmpeg 音声抽出を実行。
3. 文字起こしを保存し、1536 次元の埋め込みを pgvector へ登録。
4. 検索ツールを通した引用付き Q&A と SSE の本文・引用・完了を確認。
5. S3 オブジェクトをバックアップして削除・復元し、SHA-256 の一致を確認。
6. 定期処理と書き込みアプリを停止し、DB を dump。別の DB へ restore。
7. 暗号化キー等を保持したまま接続先を復元 DB に切り替え、API 2 Pod へ更新。
8. 同じユーザーでログインし、動画・索引・引用付き Q&A と SSE を再確認。Helm test も成功。
9. アプリを 1 Pod の初期リビジョンへ戻し、復元 DB のデータを保持した状態で再確認。
10. retention Job の成功を確認。

新規クラスタへパッケージ済み Chart を初回導入して、上記すべてを再実行しました。
[機械可読の実行結果](onprem-hardening-kubernetes-2026-10-23.json)も保存しています。
検証スクリプトはすべて成功した場合だけ `result.json` を出力します。
メール確認は既存の管理者作成コマンドによる初期管理者の手順を使い、認証条件は緩和していません。
検証用サーバーの応答 ID や S3 クライアント終了処理の不備は修正後に検証しています。

## 署名付き配布と更新

`On-prem Release` を追加しました。最新 main の push CI 成功を既存ポリシーで確認し、
amd64・arm64 のビルドとスキャンを読み取り権限で実施します。別のランナーで、アプリを
実行せず GHCR への公開と GitHub OIDC による来歴・SBOM 署名を行います。
Chart と全イメージを束ねた manifest にも署名します。

導入用の検証スクリプトは、署名者のリポジトリ・ワークフロー・main ref・ソース SHA を固定し、
Chart のバイト列と全イメージの検証が通った後だけ Helm の値を出力します。改ざん、別 SHA、
別レジストリ、不正な署名・ダイジェストで止まり、既存の値を保持することをテストしています。
配布ワークフローの最後には、実際の署名を確認して取得したイメージと Chart で同じ Kubernetes
検証を行う staging ジョブを設けました。毎日のオンプレ再検査も追加しています。

新規ワークフローの main 上での初回実行、実際の GHCR 公開と OIDC 署名は、マージ後の確認事項です。
ローカルのモックテストを実際の署名成功とは扱っていません。導入先が未定のため本番への接続や
自動反映は設定していません。本番へは検証済みの同じ digest を運用担当者が承認して反映します。

具体的な取得・署名検証・更新手順は [配布ガイド](../guides/on-premises-releases.md)を参照してください。
実サイトの TLS/Ingress、実モデル、GPU、基盤の障害耐性、運用の RPO/RTO は現地検証が必要です。
